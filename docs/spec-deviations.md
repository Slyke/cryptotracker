# Specification deviations

No deviation weakens the strict read-only upstream boundary. Market and chain integrations use allowlisted read operations (including Subscan's read-only lookup POST); Kraken private calls are constrained by an immutable query-only allowlist.

The following implementation differences are deliberate and visible:

1. **Cross-surface transfer basis.** Exact Kraken/address matches preserve both source records, evidence, fee treatment, and internal-transfer classification, and the Kraken calculation does not recognize transfer proceeds. When a tracked-address source lot is not identifiable from imported data, an inbound Kraken transfer remains unknown-basis instead of inventing basis. Automatic lot-level basis carry from an address-side lot is therefore limited to cases where the source basis is actually available.

2. **Kraken permission introspection.** Kraken permission inspection is best-effort because it is not exposed consistently for every key/account. When unavailable, diagnostics report “unverified” and the immutable endpoint allowlist remains the enforcement boundary. If inspection is available and reports write capability, Kraken activation is refused.

3. **Development audit advisory.** Production dependencies audit with no known vulnerability. The currently published SvelteKit release retains a development-only dependency on `cookie@0.6`, which npm reports as low severity. There is no non-breaking upstream version with a compatible corrected dependency range at the time of implementation.

4. **Generic JSON5 environment references.** The earlier 0.2 specification prohibited generic environment-to-configuration mapping without describing file-declared references; version 0.3 incorporates the implemented behavior. Both JSON5 files resolve exact whole-value `${ENV_VAR}` references recursively before validation. This is not an implicit environment-name-to-object-path mapper: the file explicitly declares every target location, unset variables become `null`, present empty variables remain empty strings, and the resulting object still undergoes full schema validation. The specification-required direct overrides remain available for compatibility and retain higher precedence.

5. **Coinbase public candles endpoint and quote currency.** The earlier 0.2 example used `api.coinbase.com`; version 0.3 corrects the baseline to Coinbase’s keyless Exchange candle API at `api.exchange.coinbase.com`. The bundled BTC, ETH, and SOL mappings use supported USD products. Requests for CAD or another display currency retain Coinbase’s native USD observation and derive only the quote conversion from same-bucket CoinGecko USD/display-currency observations, with derived provenance exposed in the API, WUI, and exports. No Coinbase credential or private endpoint is introduced.

6. **Enabled-asset mainnet expansion.** The earlier 0.2 specification’s address scope named Bitcoin, Ethereum, and Solana; version 0.3 incorporates the implemented expansion into the baseline. Dogecoin mainnet is supported through BlockCypher’s read-only full-address endpoint, and Polkadot mainnet is supported through Subscan’s read-only transfer lookup when a Subscan API key is configured. The address form exposes only mainnets represented by currently enabled market assets, groups known tokens such as SHIB under Ethereum, and marks an enabled network unavailable instead of accepting an address when its reviewed provider is not configured. Enabled tokens remain an explicit per-address selection; changing that selection resets only the provider cursor and queues a read-only history replay while preserving imported evidence. No signing, broadcast, wallet-secret, or arbitrary upstream-origin capability was added.

7. **Ledger-reconstructed Kraken Earn history.** Kraken’s current Earn allocation endpoint does not return a historical balance series, and exact account snapshots exist only from the time CryptoTracker begins observing the account. To avoid presenting a today-only graph when older query-ledger evidence is available, Earn history before the first exact snapshot is reconstructed from Kraken’s immutable staking allocation, deallocation, auto-allocation, and reward ledger entries. Reconstructed points retain their ledger timestamps and are superseded by exact observed snapshots where those exist. Historical valuation still requires a trustworthy cached market observation; missing prices remain missing rather than being interpolated or fetched from a write-capable endpoint.

8. **Locally observed Kraken Earn rates.** Kraken’s query-only Earn Strategies endpoint exposes current APR estimates and compounding metadata, but no historical rate endpoint. CryptoTracker therefore records a timestamped strategy-rate observation during each Kraken account refresh and begins the APY graph at the first local observation. It explicitly reports that earlier dates cannot be backfilled. Projected APY is calculated from the reported APR only when Kraken reports automatic compounding and a usable payout frequency; no historical or compounding rate is invented.

Provider-reported partial history, unavailable historical prices, unknown cost basis, stale cache state, derived CoinGecko candles, and derived quote conversion are modeled data-quality states rather than deviations; they are returned in APIs/exports and exposed in the WUI.
